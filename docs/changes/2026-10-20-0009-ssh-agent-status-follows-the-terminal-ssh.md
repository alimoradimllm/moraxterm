# Make the SSH-agent status follow the ssh the terminal runs, and explain why an agent is unavailable

`ssh_agent_status` ran a bare `ssh-add -l`, so it asked whichever `ssh-add` was first on PATH. On this PC that is the Git/MSYS build, while the terminal starts a bare `ssh` and Windows' own `ssh-agent` service is a different agent. I measured earlier that the native Windows `ssh-add` and the MSYS `ssh-add` cannot read each other's agent (`error fetching identities: invalid format` / `Bad file descriptor`), so the status could say "available" for an agent the terminal's `ssh` never uses, and "unavailable" with no reason. Now the command picks the `ssh-add` that sits in the same folder as the first `ssh` on PATH, runs it without a console window, and classifies the result from both output streams into: keys (with count), no identities, not running, unreadable (mixed OpenSSH builds), or failed (first line of output). For the Windows build with the service stopped or disabled it says which and gives the administrator command to start it.

Verified: `cargo test` in `tauri-ui/src-tauri` passes (18 passed, 2 ignored) with four new tests built from real outputs I measured on this PC (the classifier on both builds' texts, the status wording, the `sc` service text, and the PATH walk including a folder with `ssh-add` but no `ssh`); `cargo fmt --check` is clean. `scripts/ui_agent_status_test.py` calls the real command in the built exe under controlled PATHs against a throwaway MSYS agent holding one generated key: inherited PATH gives "agent unavailable: no ssh-agent is reachable..."; native first gives "the Windows ssh-agent service is disabled" plus the administrator command (the real service state here); MSYS first reports "no identities" then "1 identity" after the key is added; native first against that same MSYS agent says an agent answered in a format this ssh-add cannot read. 7/7 checks passed on two consecutive runs, and afterwards only the MobaXterm agent was running. Mistakes on the way: my first cleanup used the pid that `ssh-agent` prints, which is an MSYS-internal pid and not a Windows one, so a throwaway agent was left running twice; I stopped those two by checking their command line for the test's temp folder, and the script now finds the agent by that folder name and fails if any is left.

Open: the Windows ssh-agent service was never started here (it is disabled and starting it needs an administrator), so "Windows agent with keys" is covered by unit tests only, not a live agent. The app cannot start an agent or let the user choose one, and the Settings UI has no agent selector. An SSH login that uses an agent key was not run. The status still depends on PATH order: it follows the first `ssh` on PATH, which is what the terminal starts, but a user with two OpenSSH builds gets two different answers depending on their PATH.

Docs: updated docs/REMAINING_WORK.md (the SSH-agent status gap and the SSH-trust list) and the AGENTS.md "Known open work" line about SSH-agent status.
