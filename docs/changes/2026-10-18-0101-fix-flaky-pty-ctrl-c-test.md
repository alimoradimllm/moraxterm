# Fix the flaky Linux Ctrl+C PTY test that hung CI

The Linux CI job failed on main twice (20:03 and 20:37) and on the UI pull request with the same symptom: pty_processes_ctrl_c_as_interrupt "has been running for over 60 seconds" until the step timeout killed it. The test ran sh -i -c with an endless loop, wrote Ctrl+C immediately, and waited for the shell to exit. That only worked when Ctrl+C arrived before the shell had installed its handler (the shell was then killed by SIGINT). Once the shell was ready, an interactive shell correctly survives Ctrl+C and returns to its prompt, so the read never ended. Pinned to one busy core the old test hung in 14 of 60 runs. The test now starts an interactive shell, waits for the loop to print a computed marker, sends Ctrl+C, then runs a second command and requires its output (which can only happen if the loop was stopped), then exits the shell. A 30 second timeout turns any hang into a failing test with a message, and a read_until helper does the waiting.

Verified: on Debian WSL the rewritten test passed 40 of 40 runs unloaded and 40 of 40 pinned to one core with three busy-loop neighbours (the condition that hung the old version 14 of 60 times); all three PTY tests pass; on Windows the full rust-core suite passes, including the 14 ConPTY tests. A first rewrite that only waited for a ready marker was tested too and still timed out, which showed the real problem was the shell surviving Ctrl+C, not only the race.

Open: the new test has not run on GitHub yet. The ctrl_d (EOF) and resize tests were not changed; ctrl_d passed 40 of 40 under the same contention. The test depends on /bin/sh being an interactive POSIX shell that echoes ^C; it passed on Debian's dash.
