# Run the Telnet, VNC and SSH launch checks in the built exe, and test the real clients against loopback servers

PR #23 added a host check to the Telnet and VNC launch paths by reading the code only. This change runs it. `scripts/ui_telnet_vnc_test.py` starts the built exe with a throwaway profile on its own debugging port and calls the real `start_terminal` command with option-like hosts (`-l`, `-oProxyCommand=calc`, `-`), a host with a space, and a normal loopback host, for Telnet, VNC and SSH (option-like host and user name). No code in the app changed.

Verified: 12/12 checks pass in the exe built from `main` at `bc35a83`. Every option-like or spaced Telnet and VNC host is refused with "must not start with '-' or contain spaces or control characters"; so are an option-like SSH host and user name. A normal loopback host passes that check and stops at the client lookup: "Telnet client is unavailable: telnet.exe" and "VNC client is unavailable: vncviewer.exe". Separately, in Debian WSL, real `telnet 127.0.0.1 <port>` connected to a throwaway Python server and echoed a typed line, and real TigerVNC 1.15.0 `vncviewer 127.0.0.1:<port>` connected to a throwaway RFB server and answered `RFB 003.008`. These are the exact argument forms the app builds. Nothing left the machine.

Open: this Windows host has no `telnet.exe` or `vncviewer.exe` (`where` found neither), so a full Telnet or VNC session through the app was not run on Windows; only the checks before the client starts, and the clients themselves on Linux. The Windows Telnet client is an optional Windows feature that needs elevation to enable, and no VNC viewer is bundled, so a user without one gets the "client is unavailable" message. Whether that message tells the user how to install one was not checked.
