# Session folders with sub-folders and drag and drop in the React UI

The sidebar session list is now a real folder tree. The New folder button (which used to show "Folder management is not available in the React workspace yet") creates a folder, or a sub-folder inside the selected one. Sessions and whole folders can be dragged onto a folder to move them; hovering a closed folder while dragging opens it, a "drop here" strip moves things to the top level, and a folder cannot be dropped into itself or its own sub-folders. The same actions are in a right-click menu (session: Open, Edit, Move to a listed folder; folder: New sub-folder, Rename, Delete, Move to), so nothing depends on dragging. Folders show a session count and open or close with a click; the open or closed state is remembered. Deleting a folder keeps its sessions and moves them up one level. A session's folder is the existing folder field, stored by the Rust side as before, so a sub-folder is a path such as Work/Prod; moving a folder rewrites the path of every session below it. Folders that hold no session are kept in local storage because the session store has nowhere to keep them. The session editor's Folder field now suggests the existing folders. All tree logic is in src/folders.js (pure functions with 14 unit tests), the interface is src/SessionTree.tsx. If saving any moved session fails, the whole change is undone in the interface and the user is told.

Two environment changes were needed. tauri.conf.json sets dragDropEnabled to false: Tauri 2 on Windows otherwise captures drags for file drops and the page never receives dragenter, dragover or drop. The app also reads MORAXTERM_DATA_DIR for its session database, because on Windows the data folder comes from the OS and ignores APPDATA, so the UI test scripts previously wrote their test sessions into the real database. ui_launch_test_instance.py now sets that variable and a private WebView2 data folder and seeds one Local Shell session; ui_multiexec_test.py now replaces the page's clipboard with an in-page stub so it never reads or writes the real clipboard; cdp_driver.py enables focus emulation.

Verified: 31 unit tests pass (14 new for folders); typecheck, vite build, cargo fmt --check, cargo test (9 passed, 2 ignored), node --check and git diff --check pass. In the built exe on a throwaway profile, the new scripts/ui_folders_test.py passes 24 of 24: it creates a folder and a sub-folder through the UI, moves sessions and a folder with sub-folders, refuses a move into itself with an explanation, moves a session through the right-click menu, and then checks the saved folders in the database after a page reload and after a full app restart, plus rename and delete. ui_smoke_test.py passes 9 of 9 and ui_multiexec_test.py passes in 4 of 4 fresh runs. A screenshot of the tree and of the menu was reviewed. A first run of these tests wrote test sessions into the real session database; only those three rows (hosts ending in .invalid) were removed and the real sessions were checked unchanged afterwards.

Open: the drag and drop is verified by dispatching the real DOM drag events (dragstart, dragenter, dragover, drop, dragend with a DataTransfer) to the app's own handlers. A real mouse drag could not be tested: synthetic OS input starts the drag and the OS ends it immediately, so a person dragging with a mouse in WebView2 has not been confirmed to work end to end; the right-click menu is the tested path that works without dragging. The drop target highlight and the opening of a folder while hovering during a drag were not visually checked. Moving a session whose name collides with another folder is not an issue because folders and sessions are separate, but two sessions of different types with the same name are one database row (the store keys on name), which is an existing limitation. Empty folders live only in this computer's local storage and are lost if it is cleared. Sessions in a folder cannot yet be reordered by hand; they sort by name. Linux behaviour of the drag setting was not checked.
